# 中继链路排查与可靠传输验证

**当前实验设置更新：后续所有组统一使用 1.0 m/s、阈值 0.4。下述 1.2 m/s 是本次排查时的历史条件，已有日志不改写。**

## 已有证据

对齐 20261030T135227.308010Z 的相机检查记录与 20261030T134654.282842Z 的中继日志：

- 原图观察时间戳范围为 92.566–103.917 仿真秒。该范围内中继有 84 条已返回发布调用的日志。
- 观察程序全程收到原图 83 帧、中继输出 31 帧；其中中继输出 28 帧在上述原图时间戳范围内，范围内有 56 条发布日志未被该观察订阅者接收到。
- 26 个原图和输出共同时间戳的接收时间差约 2.3–9.1 毫秒。
- 整份中继日志 1721 行均为 ZERO_DELAY，选中帧与输入时间戳相同，无有意图像延迟。
- 控制器在图像时间戳 13.002 之后超过 2 秒未更新，里程计继续更新；中继日志记录了 13.036、13.135、13.333 等后续图像的发布调用。

这将主要排查方向指向中继输出至订阅者的传输/接收路径，不能仅凭这些记录断言具体 DDS、网络或操作系统根因。原相机接收也存在订阅者之间的帧数差异。

## 本次修改与验证边界

- 中继输出默认改为 reliable、keep-last 深度 1；相机输入仍用原 sensor-data QoS。
- 控制器新增 image_reliability 参数，默认 best_effort 保留原相机直连方式；中继试验显式选择 reliable。
- 中继日志追加回调开始、发布返回的单调时间、输入间隔、准备耗时、发布调用耗时和上一次日志写入耗时。
- 检查脚本默认可靠订阅中继输出；若检查旧版中继，使用 `--relay-reliability best_effort`。
- 在这次可靠传输修改时，速度 1.2、阈值 0.4、传感器超时 2.0 秒均未改变；随后用户将后续实验速度统一设为 1.0 m/s。

Reliable 为丢失样本提供重试能力，但不保证每帧都能在 2 秒内送达。队列深度 1 用于限制待处理历史帧；仍需观察是否存在重传等待、源图像滞后和 publish 阻塞。
ROS 2 官方参考：[QoS 策略与兼容性](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Concepts/Intermediate/About-Quality-of-Service-Settings.rst)。

后续 Ubuntu 观察记录显示两路 30 秒内分别收到 101/103 帧，最大间隔约 1.965/1.970 秒；后续也完成了使用 reliable 的行驶试验。当前原始试验日志见 [证据目录](../results/delay-replay-2026-10-30/README.md)。这些观察支持链路改善，但不能证明超时根因已消除；2 秒超时阈值保持不变。Windows 验证范围见证据目录的验证记录。

## Ubuntu 操作

停止旧控制器和中继，运行共享目录里的更新脚本：

```bash
bash /mnt/hgfs/VM_share/delay-replay-2026-10-30/scripts/update_relay_transport.sh
```

该脚本备份被替换的旧源码，更新当前项目后构建并运行测试。不会改动场景或已有实验日志。
看到 `UPDATE_COMPLETE` 后，保留 Gazebo 运行，先不启动行驶控制器。

终端 B：

```bash
bash ~/delay-replay-2026-10-30/scripts/run_relay.sh 0
```

另一个终端检查 30 秒：

```bash
bash ~/delay-replay-2026-10-30/scripts/check_camera_streams.sh
```

先检查两路更新时间和接收情况，再重置场景、中继，进行完整 0 秒行驶对照：

```bash
bash ~/delay-replay-2026-10-30/scripts/run_relay_baseline.sh
```

这个行驶脚本明确请求 reliable；不要只更新发布端而继续用旧命令的 best_effort 订阅来判断可靠传输效果。
直连原相机仍使用原命令，或明确设置 `-p image_reliability:=best_effort`。

检查通过后，所有后续延迟组都使用同样的可靠传输配置，重新采集 0 秒对照；旧 best_effort 试验保留为调试记录，不混作同条件对照。
